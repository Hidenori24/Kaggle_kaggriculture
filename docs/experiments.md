## 2026-08-11: crowded-market-price-floor

- 経緯: ユーザーからの報告で、安定版が最近の対戦で負け始め、改善版（`replay_policy`）の実スコアも最高2,500点前後から1,900点前後まで下落していた。ユーザーが共有した直近2件のKaggleリプレイ（自分視点で敗北、報酬97,862 vs 109,804 と 61,465 vs 87,144）を解析した。
- 両リプレイとも共通パターン: 序盤〜18日目頃までは対戦相手と互角以上だが、18〜20日目を境に相手の資金成長が急加速し、以降差が開き続ける。同時に市場価格を見ると、`MELON`が250→4〜10、`FERTILIZER`が100→32〜34、`MILK`/`WOOL`が160/200→1〜30まで暴落していた。両ゲームとも初期価格は同一（`CARROT35, EGG50, FERTILIZER100, MELON250, MILK160, STRAWBERRY120, TOMATO60, WHEAT25, WOOL200`固定）であることを確認済み。
- 原因分析: `replay_policy.py`は単一の公開リプレイから書き起こした固定行動列を再生するだけで、現在の市場価格を見ずにSELL数量をそのまま実行していた。似た戦略（本アルゴリズム自身の由来である公開ノートブックの模倣を含む）を採用する対戦相手が増えたことで、特定品目（動物性商品・投機的作物）の供給過多が発生し、価格が暴落したタイミングでも構わず投げ売りしてしまい、序盤の優位を終盤で失っていたと考えられる。
- 対策: `_safe_market`に価格フロア機構を追加。各品目の初期基準価格（`_PRICE_REFERENCE`）に対する現在価格の比率に応じて、SELL予定数量を段階的に絞る（50%以上で全量、25〜50%で半量、10〜25%で2割、10%未満は保留）。保留分は最終日の`_terminal_market`で必ず清算されるよう、`_terminal_market`側もSELL予定数量控除後の残余在庫を正しく計算するよう修正した（従来は同一品目に部分SELLが既にあると残りを見送っていたバグを合わせて修正）。
- 検証: `python -m pytest -q`は16件成功（価格フロアの分岐を検証する新規テスト3件を追加）。`python scripts/simulate.py --episodes 5`はrandom相手に平均約189,557点で、価格暴落が起きないrandom対戦では既存挙動とほぼ同等（想定通り、フロアはランダム相手では滅多に発動しない）。共有された2件の実リプレイの観測列に新方針を適用したところ、同一ステップ・同一価格条件でのSELL計画金額が旧方針比で+7.3%（144,384→154,943）、+8.6%（110,810→120,371）と増加し、暴落価格での投げ売り抑制効果を確認した（状態遷移の反実仮想までは再現していない概算値）。

## 2026-08-11: preempt-shift-price-floor-double-clamp-fix

- 上記の価格フロア導入直後にレビューした結果、`_preempt_shift`内部が独自に`_safe_market(obs, action)`（価格フロア有効）を呼び直しており、`agent()`側で既に一度フロア適用済みのSELL数量へ再度フロアをかけてしまうバグを発見した。例: 元の要求5個がフロアで1個へ縮小された後、`_preempt_shift`内の再クランプで`1 * 0.2`が切り捨てられ0個になり、注文自体が消える。

## 2026-08-11: shed-pressure-animal-starvation-regression

- 経緯: 提出直後の2件のKaggleリプレイ（自分視点で敗北、報酬48,352 vs 49,501 と 42,255 vs 60,798）をユーザーが共有。序盤〜中盤は互角以上だったが、両試合とも22〜24日目付近で自分側の飼育動物数が急減（14→1、14→0）し、そこから相手との差が開いた。
- 原因: 価格フロア機構が、価格が暴落した品目（WOOL・MELON・MILK・FERTILIZERなど）のSELLを保留してshed（総容量100）へ滞留させ続けた結果、shedが18日目以降ずっと満杯（100/100）に固定された。shedが満杯だと新規のWHEAT購入がshedへ入庫できず（`_projected_shed`の`room`が0になる）、飼料WHEATの補充が止まり、動物が給餌不能（`consecutive_unfed`上昇）となって餓死・消滅した。旧版（価格フロア導入前）の同時期のリプレイでは、shedは55〜90程度で推移しており満杯に固定されることはなかった。
- 対策: `_safe_market`に「shed圧力弁」を追加。`_projected_shed`の合計占有量が`_SHED_PRESSURE_RELIEF`（80/100）以上になった時点で、その呼び出しに限り価格フロアを自動的に無効化し、保留していた低価格品目も通常通り売却してshedを空ける。これにより、価格暴落時でもshedが満杯に固定されず、WHEAT補充と動物の給餌ループが継続する。
- 検証: 実際に満杯（shed合計100、WOOL19保有）だったリプレイの18日目の観測をそのままエージェントへ入力し、修正前は`FERTILIZER`（価格5、基準100の5%）が保留され0個になっていたのに対し、修正後はshed圧力弁が働きtape本来の数量（STRAWBERRY6・WOOL6・MILK9・FERTILIZER5等）が売却され、shedが空くことを確認した。回帰テスト`test_price_floor_stands_down_when_shed_is_under_pressure`を追加。`python -m pytest -q`は18件成功、`python scripts/simulate.py --episodes 5`はrandom相手に185,341〜197,896点で既存挙動と同等。
- 教訓: 個別のSELL単位でのみ価格フロアを検証し、shedという共有リソースへの累積的な副作用を見落としていた。今後、`_safe_market`へ変更を加える際はshed占有率の時系列も必ず確認する。

## 2026-08-12: measured-market-timing (harness first, then change)

## 2026-08-15: 1,300の天井 — 固定tape方式の限界を確認

- ラダー実測: SELL並べ替え版（提出前ゲートで現行版に16戦全勝・+2.24%）を2本目として並走させた結果、**両版とも約1,300で頭打ち**（1本目 最高`1,323`、2本目`1,260`）。**ゲート上の+2.24%は、頭打ち値を動かさなかった。**
- 解釈: レーティングの頭打ちは「相手プールに対する勝率が50%になる点」で決まる。報酬2%差のほぼ同一な2エージェントは、第三者に対する勝率がほぼ同じであり、同じ帯へ収束する。**同一tapeへのラッパー調整は、何%積んでも天井を動かさない。**
- したがって残る余地は「売り方」ではなく「何を作るか」である。市場パラメータから各品目の崩壊余力（価格が床に達するまでの超過供給量）を算出すると、うちの生産物は全て脆い側に偏っていた: `WOOL`約59、`STRAWBERRY`約63、`MILK`約76、`MELON`約158。対して`EGG`はlog曲線で事実上崩壊せず、実敗戦`93332940`では`50`→`154`（3倍）へ**上昇**していた。`CARROT`約918、`WHEAT`もlog曲線で25→54へ上昇。
- tapeの生産構成: 動物は`COW`8・`SHEEP`6のみ、構造物は`BUILD_PASTURE`14のみ、種は`WHEAT`92・`STRAWBERRY`42・`MELON`24。**`GOOSE`・`EGG`・`CARROT`・`TOMATO`は完全にゼロ。**
- 動物性能では`GOOSE`が突出している。費用`300`（最安）、初収穫`4日目`（最速、`COW`は8・`SHEEP`は6）、産出間隔`1日`（最頻、`COW`2日・`SHEEP`3日）、産物`EGG`（最も価格耐性が高い）。混雑相場では明確に優位なはずである。
- **置換実験は完全に失敗した。** `BUILD_PASTURE`→`BUILD_COOP`、`COW`/`SHEEP`→`GOOSE`（`PICKUP`/`PLACE`/`BUY_ANIMAL`）を書き換えた版は、対 現行版で**0勝12敗・平均 −96.53%**。売却側`SELL MILK`/`WOOL`→`SELL EGG`も併せて書き換えた版と**数値が完全に一致**しており、動物収入を失ったのではなく**農場全体が崩壊している**。構造物の種類を1つ変えるだけでtapeの噛み合ったユニット動線が総崩れになる。Thomasのtapeを移植した際（−81%）と同じ壊れ方である。
- **結論: 固定tape方式の天井は約1,300。** ラッパーで触れるのは市場注文の並び順程度（実測+2.24%だが天井は動かない）で、生産構成に手を入れると即座に壊れる。1,300を超えるには、tapeの再生ではなく**状態依存ポリシーの実装**が必要である。今セッションで整備した測定基盤（`benchmark.py`＝回帰検出、`head_to_head.py`＝相対比較、ラダー実測＝最終判定）はその開発にそのまま使える。
- ただし測定基盤の限界も判明している。`benchmark.py`は市場を奪い合わない相手のため増産系の変更を過大評価する（idle-hands候補が+1.99%と出て直接対決で24戦全敗）。`head_to_head.py`も完全ではない（旧価格フロア版との比較が−0.26%だったが、ラダーでは約1,000対1,330と明確に差がついた）。**ローカル指標は方向の目安であり、最終判定はラダー実測でしか下せない。**

## 2026-08-15: 崩壊相場ハーネスと、ガチョウ案の最終判定

- 前節の「置換すると壊れる」という結論は**早すぎた**ので訂正する。診断の結果、崩壊の原因は動線の破壊ではなく**shed飽和**だった。ガチョウは`interval=1`で毎日EGGを産むが、**tapeにはEGGの売却注文が存在しない**ため16日目にshedが満杯（100）になり、以降WHEATも買えず収穫物も破棄され、24日目に動物全滅・28日目に雑草46・資金0まで荒廃していた。
- また、当初の「`SELL MILK`/`WOOL`を`SELL EGG`へ書き換える」検証は**無効だった**。`_safe_market`が`_base()`内で在庫ゼロのMILK/WOOL注文を既に削除しており、ラッパーがリネームする対象が残っていなかった。L4とL5の数値が完全一致していたのはこのためである。
- EGG売却を**新規注入**する形に修正すると、通常相場で−96.5%→−62.2%まで回復した。それでも大敗であり、理由は測定領域にある。直接対決の相手は1体のみでMILK/WOOL相場が崩れないため、**EGGの「混雑相場で価格耐性が高い」という長所が発現する条件が存在しない**。
- そこで`scripts/stress_market.py`を追加した。環境は`marketParams`の上書きを受け付け、価格はこのテーブルと在庫の純関数なので、脆い品目の`base`を下げることで**最初から崩壊した相場**を作れる（`MELON`4 / `WOOL`2 / `MILK`5 / `STRAWBERRY`12 / `FERTILIZER`6、実敗戦`93332940`の終値に基づく）。`--profile fresh`（上書きなし）での同一コード対決は`+0.00%`で健全性を確認済み。
- **ガチョウ案の最終判定（崩壊相場、6seed×両席=12戦）: 4勝8敗、平均マージン +113.58%。**
- **不採用とする。** 平均は大きく正だが、これは少数の大勝によるもので、**勝率は4勝8敗と負け越している**。レーティングの頭打ち値を決めるのは勝ち幅ではなく勝率であり（1,300で頭打ちした理由そのもの）、その指標では自身の主張が最も通るはずの領域ですら不合格である。
- **測定上の教訓: 平均マージンと勝率は真逆を向きうる。** 今後の採否判定は勝率を主軸とし、平均マージンは補助指標として扱う。`head_to_head.py`と`stress_market.py`はいずれも両方を出力する。
- 注意: `stress_market.py`は戯画であって模擬ではない。相場がどう崩壊するかについては何も言わず、崩壊後にどう稼ぐかだけを測る。崩壊相場向けに調整した方針は、試合の大半を占める通常相場で大きく誤るため、**必ず`head_to_head.py`と併用し、単独で判定に使わない**。
