# ブランチ運用

## 目的

現在の最高記録を安定版として保存し、改善候補を別系統で検証する。Kaggleへ提出するのは、検証済み候補を意図的に `submission` へ反映した場合だけにする。

## ブランチの役割

| ブランチ | 用途 | Kaggle提出 |
| --- | --- | --- |
| `feature/*` | テスト・小変更 | しない |
| `experiment/*` | 戦略候補の実験 | しない |
| `main` | 検証済みコードの統合 | しない |
| `baseline/score-*` | 最高スコア版の凍結保存 | しない |
| `submission` | 意図的に選んだ提出候補 | pushで実行 |

## 改善の流れ

1. `experiment/<topic>` を作成する。
2. ローカルテスト、3エピソード評価、拡張評価、過去JSONの回帰確認を行う。
3. 候補が不採用なら実験ブランチだけに残す。
4. 採用する場合は `main` に統合し、同じコミットを `submission` に反映する。
5. `submission` のpushでCI・パッケージ検証・Kaggle提出を実行する。
6. 提出後、コミットSHA、パッケージSHA-256、提出ID、スコアを実験履歴へ記録する。

## 安定版の扱い

最高スコア版は `baseline/score-<score>` とタグで保存する。改善候補が悪化しても、安定版を変更・削除・force-pushしない。

現在は1951.2版を安定版候補として扱い、PASS修復候補は実験版に留める。Kaggleの最新提出枠を維持するため、未検証候補を自動提出しない。

## Actions

- `ci.yml`: `main`、`feature/**`、`experiment/**`、`baseline/**` のテストとシミュレーション。
- `submit.yml`: `submission` へのpushだけで提出処理を開始。
- `concurrency` により同時提出を防止する。
- Secret未設定、テスト失敗、シミュレーション不合格、重複コミット、提出回数制限超過時は停止する。
